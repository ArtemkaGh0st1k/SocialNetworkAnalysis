### Архитектура и принцип работы 

1. Сбор данных `collect_friends.py`
- Авторизация VK API
- Запрос `friends.get` для исходного пользователя и для каждого его друга
- Закрытый профиль? --> Записываем пустой список
- Превышен лимит запросов? --> Ждём и повторяем запрос
- Другая ошибка? --> Сохраняем прогресс и прерываем сбор
2. Построение графа `build_graph.py`
- Вершины: исходный пользователь и его друзья
- Рёбра: дружеские связи, вес ребра равен числу общих друзей
- Сохранение графа в `GraphML` и метрик в `JSON`
3. Визуализация `visualize_graph.py`
- Выделение сообществ методом Лувена
- Укладка графа `spring_layout`
- Сохранение рисунка в `PNG` и описания сообществ в `JSON`

Все этапы запускаются из корня проекта через `main.py`, который вызывает `run_lab3_pipeline` из `pipeline.py`:

```bash
python main.py
```

**Логика работы:**

1. Настройка доступа
Токен хранится в файле `lab1/.env`. Функция `load_dotenv()` без аргумента ищет файл от папки вызывающего модуля и выше, поэтому путь указан явно:

```python
ENV_PATH = join("lab1", ".env")
load_dotenv(ENV_PATH)
```

Чтобы данные профиля были доступны через API, в настройках приватности VK нужно открыть профиль. Подробности указаны в комментарии в начале `collect_friends.py`. Другие пользователи могут закрыть свои данные собственными настройками.

2. Получение списка друзей
Метод `friends.get` возвращает до 5000 id за один запрос. Чтобы получить длинный список полностью, используется сдвиг `offset`:

```python
while True:
    response = self.request_friends(
        user_id=user_id, count=MAX_FRIENDS_BY_REQUEST, offset=len(friends)
    )

    items = response.get("items", [])
    friends.extend(items)

    if not items or len(friends) >= response.get("count", 0):
        return friends

    time.sleep(REQUEST_PAUSE)
```

3. Обработка ошибок
Ошибки VK имеют разный смысл, поэтому обрабатываются по-разному:

| Код | Ситуация | Действие |
|---|---|---|
| 15, 18, 30 | Нет доступа, страница удалена, профиль закрыт | Записать пустой список и продолжить |
| 6, 29 | Превышен лимит запросов | Подождать и повторить, максимум 3 раза |
| Остальные | Например, неверный токен | Сохранить прогресс и остановиться |

Если записать пустой список при превышении лимита, у человека ложно исчезнут все друзья, и граф исказится без каких-либо ошибок.

4. Сохранение прогресса
Сбор занимает время, поэтому результат сохраняется каждые 10 друзей и при любом прерывании. При повторном запуске обработанные друзья пропускаются. Запись идёт через временный файл, чтобы сбой не испортил уже собранные данные:

```python
temp_path = path.with_suffix(".tmp")
with open(temp_path, mode="w", encoding="utf-8") as file:
    json.dump(data, file, indent=4)

os.replace(temp_path, path)
```

Результат сохраняется в файл `friends_<id>.json`:

```json
{
    "user_id": 123,
    "friends": [456, 789],
    "friends_of_friends": {
        "456": [123, 789, 111],
        "789": []
    },
    "unavailable": [789]
}
```

Поле `unavailable` отличает закрытый профиль от человека, у которого действительно нет друзей.

5. Построение графа
Вершины графа: исходный пользователь и его друзья. Друзья друзей отдельными вершинами не становятся, их списки нужны только для поиска связей и подсчёта общих друзей.

Дружба проверяется с обеих сторон, потому что закрытый профиль виден в списке открытого:

```python
return user_b in self.friend_lists[user_a] or user_a in self.friend_lists[user_b]
```

Исходный пользователь есть в списке каждого друга, поэтому он не учитывается в весе ребра, иначе все веса были бы завышены на 1:

```python
common = self.friend_lists[user_a] & self.friend_lists[user_b]

return len(common - {self.source_id})
```

Атрибуты вершин: `friends_count`, `available`, `is_source`. Атрибуты рёбер: `weight`, `weight_known`. Если хотя бы один профиль пары закрыт, вес неизвестен и `weight_known = False`.

6. Метрики графа
Метрики считаются для полного графа и для графа без исходного пользователя. Исходный пользователь связан со всеми, поэтому в полном графе диаметр не больше 2, а коэффициент кластеризации завышен. Диаметр считается по наибольшей компоненте связности, потому что для несвязного графа он не определён.

7. Выделение сообществ
Используется метод Лувена. Исходный пользователь и веса в расчёте не участвуют:

```python
communities = nx.community.louvain_communities(
    self.friends_graph, weight=None, seed=STATE
)
```

- С исходным пользователем границы между группами размываются, потому что он связан со всеми.
- С весами все закрытые профили становятся отдельными сообществами, потому что вес 0 у их рёбер означает «неизвестно», а алгоритм считает такие связи отсутствующими.

8. Укладка графа
`spring_layout` отталкивает несвязанные вершины далеко и сжимает основную часть сети, поэтому укладка считается только для наибольшей компоненты. Малые компоненты ставятся по кольцу вокруг неё, а исходный пользователь в центр. Расстояние до вершин на кольце ничего не значит.

9. Оформление рисунка
- Цвет вершины: сообщество. Три крупных сообщества имеют свой цвет, остальные показаны серым.
- Размер вершины: число друзей в логарифмической шкале, от 100 до 1000. Закрытый профиль показан полым и с минимальным размером.
- Толщина ребра: число общих друзей. Рёбра с неизвестным весом показаны тонкой светлой линией.
- Рёбра исходного пользователя показаны бледно, иначе они закроют весь рисунок.

Значения приводятся к нужному диапазону нормализацией:

```python
low + (high - low) * (values - values.min()) / (values.max() - values.min())
```

10. Результаты
Файлы сохраняются в папке `lab3/results`:

| Файл | Содержимое |

Файлы `friends_*` и `graph_*` содержат id реальных людей, поэтому исключены из git через `.gitignore`. Рисунок без id и имён хранится в репозитории.

При чтении графа нужно указывать тип вершин, иначе id будут прочитаны как строки:

```python
nx.read_graphml(graph_path, node_type=int)
```
